Mosaic / UI language mocks

Static mocks for the amber terminal direction in DESIGN.md. Nothing here is wired to behavior. The colors come from the existing Ember palette in src/renderer/styles.css; layout, type, and controls are proposals. Notes on the right of each mock explain why each choice exists. Items marked open are undecided.

Layout

Three fixed regions: tree, writing column, one status line. No tabs, inspectors, or panels. Each region sits in the same place in every mock, matching DESIGN.md's “favor stillness and predictable placement”.

Two typefaces, two jobs

Mono carries the terminal feel in chrome: tree, status, labels, buttons. Prose uses a reading face and warm white, not amber, so long sessions stay comfortable. Try the switches above. Prose family is open.

Formatting vocabulary

H1–H3 differ by size and weight, bold by weight, italic by slant. None of it depends on color, which matters for e-paper (see 06).

Implicit links

Dotted underline at rest; solid underline plus brighter text on hover/focus (“Old Tomas”). Text color stays prose-colored, so a page dense with names doesn't turn into an amber wall. How you follow a link is open.

Block gutter

A faint H3 marker left of the block with the caret tells you the structure without showing markup. A small idea, easy to drop.

Tree

Current document is inverted, not just tinted, so it survives monochrome. The pixel 3×3 mark is the only “graphic”.

Why show this

The writing column doesn't move when the tree hides: it is centered in its own region either way. This is the closest desktop analogue to a dedicated writing device.

Selection

A soft amber wash with a thin outline, so it stays readable over prose and still shows as a boxed region without color.

Caret

A thin, non-blinking amber bar. A block caret is more “terminal” but hides the letter under it in prose. Blink is a preference to decide.

Toggle gesture (e.g. a shortcut) is open.

03 — Save status / the status line's vocabulary

Normal: last revision reached disk
Places / The Lighthouse212 words■ Saved
Normal: a newer revision is being written; typing continues
Places / The Lighthouse214 words□ Saving…
Failure: stays visible until resolved, with an action
Places / The Lighthouse▲ Couldn't save — disk is full

Words plus shape

Each state has a word and a distinct glyph (■ □ ▲). Neither depends on color, so both survive a monochrome screen.

No spinner

“Saving…” is static text. Saves should be brief and frequent; an animation flickering in the corner of your eye on every pause is the kind of motion DESIGN.md asks to avoid.

Failure inverts the bar

The whole line inverts, which is loud in both amber and monochrome. It's the one place the UI raises its voice. Revisions and internals belong in diagnostics, not here.

Close Mosaic

“The Lighthouse” has writing that couldn't be saved.

The disk is full. Free some space and try again, or keep writing and close later.

When this appears

Only when closing can't settle the save. On a normal close Mosaic finishes the pending save and quits; no “Save changes?” prompt every time.

Safe default

Keep writing has focus (visible ring), so pressing Enter by reflex never loses work. Discard is set apart and fully worded rather than relying on red.

Tree marker

The * after the name marks writing not yet on disk — a terminal-era convention that needs no color.

Inline, not modal

You can keep typing while deciding, and nothing on disk or on screen gets replaced silently. The notice sits in the column, above the prose, so it pushes rather than covers.

Status agrees

The status line says Save paused so it never claims “Saved” while the conflict is unresolved.

The actual choices (and whether a comparison view is worth it) are open; this only shows how such a notice looks in the language.

The test, not the target

This isn't an X3 UI. It's mock 01 with only the color tokens swapped, to check that every meaning survives without amber: headings, bold, italic, links (solid underline), current document (inversion), save failure (inverted bar + ▲ + words).

What this buys

If the desktop UI passes this test, a later light theme, high-contrast mode, or an e-reader rendering can reuse the same visual rules even though it won't share code.

Deliberately small

Six colors (all existing), two type families, one button style, four status glyphs. That's the whole language so far. New parts should be built from these before adding anything.

Not used

No scanlines, glow, flicker, or CRT curvature anywhere near prose. If wanted later, they'd be an opt-in effect on chrome only.
